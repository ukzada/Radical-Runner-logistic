PROJECT AUDIT, BUG FIXING & UI/UX IMPROVEMENT PROMPT FOR GLM

You are a senior full-stack engineer, UI/UX designer, frontend performance engineer, and software QA specialist.

You are working on an existing project that has already been partially built. Your job is not to blindly rewrite the project from scratch. First, deeply inspect the existing codebase, understand the architecture, identify problems, and then systematically improve it.

The current project has several issues:
- Bugs and broken functionality.
- UI inconsistencies.
- Poor spacing and alignment.
- Some interactions do not feel smooth.
- The application does not feel polished or production-ready.
- Some components may be poorly structured.
- There may be unnecessary re-renders or inefficient frontend logic.
- Responsive behavior may have issues.
- Loading, transitions, navigation, and interactions may feel abrupt.
- Error handling may be incomplete.
- Some features may exist but not work correctly.

Your goal is to transform the existing project into a stable, polished, smooth, modern, and production-quality application.

1. FIRST: DEEPLY ANALYZE THE EXISTING PROJECT

Before changing code:
1. Read and understand the entire project structure.
2. Identify the framework, libraries, dependencies, architecture, and design system already being used.
3. Inspect all important pages, components, hooks, services, API calls, state management, and utilities.
4. Trace how data flows through the application.
5. Identify incomplete, duplicated, unused, or poorly implemented code.
6. Check for console errors, TypeScript errors, runtime errors, broken imports, and dependency issues.
7. Identify UI components that are inconsistent with the rest of the application.
8. Understand the existing design direction before making visual changes.

Do not immediately rewrite large parts of the application. Preserve working functionality and improve the existing architecture where possible.

2. CREATE A COMPLETE ISSUE AUDIT

Before implementing fixes, identify issues in these categories:

FUNCTIONAL BUGS
- Buttons that do not work.
- Broken navigation.
- Forms that do not submit correctly.
- Incorrect validation.
- Broken API requests.
- Incorrect loading states.
- Missing error states.
- State synchronization problems.
- Data not updating correctly.
- Race conditions.
- Broken authentication or protected routes if applicable.
- Features that partially work but fail in certain situations.

UI BUGS
- Misaligned elements.
- Inconsistent spacing.
- Incorrect padding or margins.
- Text overflow.
- Components breaking on small screens.
- Incorrect widths or heights.
- Overlapping elements.
- Broken modals, dropdowns, tooltips, or popovers.
- Inconsistent border radius, shadows, and typography.
- Poor button sizing.
- Incorrectly aligned icons.
- Horizontal scrolling caused by layout issues.

RESPONSIVE BUGS
Test and fix the application for mobile, tablet, laptop, and large desktop screens.
The UI should adapt naturally instead of simply shrinking.

Pay special attention to navigation, sidebars, tables, forms, cards, modals, dashboards, and complex layouts.

3. IMPROVE THE UI/UX

The goal is to make the application feel like a high-quality modern SaaS product, not like an AI-generated prototype.

Avoid:
- Random excessive gradients.
- Excessive glassmorphism.
- Too many rounded cards.
- Inconsistent colors.
- Oversized headings.
- Excessive animations.
- Generic AI-looking layouts.
- Too much empty space.
- Too many borders.
- Unnecessary visual effects.

The UI should have:
- Clear visual hierarchy.
- Consistent spacing and typography.
- Predictable interactions.
- Clean alignment.
- Balanced whitespace.
- Proper content grouping.
- Accessible contrast.
- Clear primary and secondary actions.
- Professional empty states.
- Helpful loading states.
- Clear error messages.

Every component should look intentionally designed.

4. CREATE A CONSISTENT DESIGN SYSTEM

Inspect the existing UI and standardize it.

Create or improve reusable design tokens for:
- Primary and secondary colors.
- Background and surface colors.
- Text and border colors.
- Success, warning, and error states.
- Border radius.
- Shadows.
- Spacing scale.
- Typography scale.
- Animation timing.

Avoid hardcoding random values throughout the project. Use reusable variables, tokens, constants, or the existing theme system.

5. MAKE INTERACTIONS FEEL SMOOTH

Improve the user experience with appropriate transitions and animations.

Focus on:
- Page transitions where appropriate.
- Sidebar transitions.
- Dropdown animations.
- Modal opening and closing.
- Hover states.
- Button interactions.
- Loading transitions.
- Skeleton loaders.
- Toast notifications.
- Tab transitions.
- Expand/collapse interactions.
- Form feedback.

Animations should be fast, subtle, natural, and purposeful. Avoid slow or distracting animations. Respect reduced-motion preferences where possible.

6. IMPROVE LOADING STATES

Implement proper states for:
1. Initial loading.
2. Data loading.
3. Button loading.
4. Form submission.
5. API processing.
6. Empty results.
7. Errors.
8. Successful actions.

Use skeleton loaders where appropriate, inline button loaders, clear empty states, friendly error messages, and retry actions when appropriate.

Avoid showing blank screens during loading.

7. FIX ERROR HANDLING

Every important asynchronous operation should handle:
- Loading.
- Success.
- Error.
- Empty responses.
- Unexpected responses.

Do not silently fail.

Errors should be understandable, explain what happened when possible, tell the user what they can do next, and avoid exposing unnecessary technical details.

Ensure errors do not permanently break the UI.

8. OPTIMIZE FRONTEND PERFORMANCE

Check for:
- Unnecessary re-renders.
- Expensive calculations running repeatedly.
- Large components that should be split.
- Unnecessary or duplicate API calls.
- Memory leaks.
- Missing cleanup functions.
- Inefficient state management.
- Large assets.
- Components rendering when hidden or unnecessary.

Optimize only where genuinely needed. Do not add useMemo or useCallback everywhere without a reason.

Prefer clean architecture over premature optimization.

9. CLEAN UP THE CODEBASE

Look for:
- Duplicate code.
- Dead code.
- Unused imports and dependencies.
- Overly large components.
- Repeated UI patterns.
- Magic numbers.
- Hardcoded values.
- Inconsistent naming.
- Poor separation of concerns.

Refactor carefully and extract reusable components, hooks, utility functions, constants, and services where appropriate.

Do not over-engineer the project. Keep the architecture simple, maintainable, and easy to understand.

10. VERIFY EVERY FEATURE

For every page and feature, verify:
1. Can the user access it?
2. Does the UI load correctly?
3. Does the data load correctly?
4. Do buttons work?
5. Do forms validate correctly?
6. Does submission work?
7. Are loading states shown?
8. Are errors handled?
9. Does the UI update after successful actions?
10. Does it work on mobile and desktop?

Trace complete user flows from start to finish.

11. DO NOT BREAK EXISTING FUNCTIONALITY

- Preserve existing working features.
- Do not remove functionality unless it is clearly broken or obsolete.
- Do not randomly change APIs.
- Do not change database schemas unnecessarily.
- Do not introduce breaking changes.
- Do not replace the entire project just because parts of it are messy.

Make controlled and incremental improvements. After each significant change, verify that the related functionality still works.

12. WORK IN PHASES

PHASE 1 — PROJECT ANALYSIS
- Inspect the complete codebase.
- Understand the architecture.
- Identify dependencies.
- Identify critical functionality.
- Create a list of issues.

PHASE 2 — CRITICAL BUG FIXES
Fix build errors, type errors, runtime errors, broken functionality, broken API calls, and critical state issues.

PHASE 3 — UI BUG FIXES
Fix alignment, spacing, layout problems, responsive issues, overflow, and broken components.

PHASE 4 — UX IMPROVEMENTS
Improve navigation, user flows, loading states, empty states, error states, feedback, and interactions.

PHASE 5 — VISUAL POLISH
Improve typography, colors, spacing, component consistency, buttons, forms, cards, tables, and modals.

PHASE 6 — PERFORMANCE AND CODE CLEANUP
- Remove dead code.
- Fix unnecessary rendering.
- Improve component structure.
- Clean imports.
- Improve maintainability.

PHASE 7 — FINAL QA
Perform a complete review covering desktop, tablet, mobile, major user flows, forms, navigation, loading, errors, and empty states.

13. IMPLEMENTATION RULES

DO:
- Inspect before modifying.
- Understand existing architecture.
- Fix root causes instead of hiding symptoms.
- Reuse existing components where possible.
- Create reusable components for repeated patterns.
- Keep code clean and readable.
- Follow good existing project conventions.
- Use TypeScript correctly if applicable.
- Handle loading and error states.
- Test changes after implementation.
- Make incremental improvements.

DO NOT:
- Do not rewrite the entire project without a strong reason.
- Do not randomly change the technology stack.
- Do not introduce unnecessary dependencies.
- Do not add animations everywhere.
- Do not overuse gradients or glass effects.
- Do not create inconsistent component styles.
- Do not use hardcoded values unnecessarily.
- Do not leave console errors or warnings unresolved.
- Do not remove existing features accidentally.
- Do not create fake functionality just to make the UI appear complete.
- Do not stop after fixing only visual issues.

14. FINAL QUALITY STANDARD

The final application should feel:
- Smooth.
- Fast.
- Stable.
- Responsive.
- Professional.
- Consistent.
- Intentional.
- Easy to use.
- Production-ready.

It should not look like a quickly generated AI prototype.

Every screen should feel like part of the same product. Every interaction should provide clear feedback. Every important feature should work correctly.

Before considering the work complete, perform a final review:
- Are there any visible UI issues?
- Are there any broken user flows?
- Are there inconsistent components?
- Are loading and error states handled?
- Does the application feel smooth?
- Does it work properly on mobile and desktop?
- Is the code maintainable?
- Would this feel like a professional product to a real user?

If the answer to any of these is no, continue improving the project.

Do not declare the project complete until the application is both functionally reliable and visually polished.
